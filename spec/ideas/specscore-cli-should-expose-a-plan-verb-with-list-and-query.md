# Idea: CLI plan Verb (list + info)

**Status:** Specified
**Date:** 2026-06-04
**Owner:** alexander.trakhimenok
**Promotes To:** cli/plan, cli/plan/info, cli/plan/list
**Supersedes:** —
**Related Ideas:** —

## Problem Statement

How might we let the specscore CLI list and query Plan artifacts the way it already does for Ideas and Features, so agents and humans can answer what plans exist and what status they hold without hand-grepping spec/plans/?

## Context

Plans (spec/plans/*.md) are not a first-class CLI artifact. The top-level verbs are idea, feature, task, issue, and proposal; there is no plan verb, so specscore plan errors with Unknown command. The pkg/plan package already parses plans (tasks, source feature, deferred-AC coverage) for lint, but exposes no plan-level Status field and no command surface. Answering what plans are open today requires ls spec/plans plus a grep over the Status line. Promoted from the sidekick seed of the same slug, captured during an open-artifact review where the missing verb forced manual grepping.

## Recommended Direction

Ship two read-only verbs that mirror the existing feature/idea contract exactly: specscore plan list and specscore plan info <slug>. plan list emits slugs one per line as text by default, supports --status filtering, --format json|yaml, and a --fields selector; plan info <slug> prints one plan's metadata. A plan's lifecycle status is read verbatim from its **Status:** line, the same trust model feature and idea use. The single substrate gap is extending pkg/plan to capture plan-level **Status:** (plus Date/Owner/Mode for info); the rest reuses the feature-list output and format scaffolding. No plan tree subcommand, because plans are flat rather than hierarchical.

## Alternatives Considered

- **Full lifecycle parity (`plan new` + `plan change-status`).** Lost because plans are generated by `specstudio:plan`, not hand-authored, so there is no demonstrated demand for CLI mutation. It widens the surface and the test burden for a workflow nobody runs today. Revisit only if plans become CLI-managed artifacts.
- **Fold plan status into `feature info`** (show the Source Feature's plan inline). Lost because it answers "what's the plan for this feature?" but not "list all plans and their status" — the actual question that triggered the seed. Discoverability is worse, and it breaks the idea/feature/plan mental-model parity.
- **Derive plan status from the Source Feature** (Feature `Stable` ⇒ plan effectively done). Lost for the MVP because it couples a read verb to the feature graph and is materially more work. The seed's pain is "can't query plans at all," not "status is subtly stale" — so trust-the-file ships the painkiller first; drift detection can follow as a lint rule.

## MVP Scope

A spike that adds plan-level Status parsing to pkg/plan and wires plan list plus plan info by reusing the feature command scaffolding, with text/json/yaml parity. Done when specscore plan list --status Approved --format json and specscore plan info <slug> both work against this repo's spec/plans/ directory.

## Not Doing (and Why)

- plan new and plan change-status — plans are generated by specstudio:plan, not hand-authored, so mutation parity solves a problem nobody has yet
- Deriving plan status from the Source Feature — directly fixes stale statuses but couples the verb to the feature graph; defer until drift is actually felt
- Plan-vs-Feature drift detection — belongs in a lint rule, not a read-only query verb
- plan tree — plans are flat, with no hierarchy to render
- Canonical plan-status enum validation — MVP string-matches whatever **Status:** the file carries

## Key Assumptions to Validate

| Tier | Assumption | How to validate |
|------|------------|-----------------|
| Must-be-true | Plans are intended to be CLI-queryable artifacts, not deliberately just files. | Confirmed during ideation — the user chose read-only `list`/`info` over leaving plans as plain files. |
| Must-be-true | Every plan file reliably carries a parseable `**Status:**` line. | `grep '^\*\*Status:\*\*' spec/plans/*.md` — all 12 plans in this repo have one. Add a `pkg/plan` parser field plus a test covering a missing/blank status. |
| Should-be-true | The `feature list` output/format scaffolding (text/json/yaml, `--fields`, `--status`) maps cleanly onto plans. | Prototype `plan list` by adapting `feature list`; plans are flatter (no tree), so it should be a strict simplification of the feature path. |
| Might-be-true | Users will later want plan lifecycle mutation or Feature-vs-plan drift detection. | Watch for follow-on seeds; do not build now. |


## SpecScore Integration

- **New Features this would create:** `cli/plan` (parent), with `cli/plan/list` and `cli/plan/info` — exact slugs TBD at spec time.
- **Existing Features affected:** none directly (additive verb). The `pkg/plan` package gains a plan-level `Status` field; the sibling `cli/feature` (list/info) is the pattern to mirror.
- **Dependencies:** builds on the existing `pkg/plan` parser; follows the `cli/feature` list/info contract for output and flags.

## Open Questions

- Should `--status` validate against a canonical plan-status set, or string-match freely? Feature and Idea validate against a defined enum; plans have no canonical status set yet (observed values: `Approved`, `Completed`).
- Should `plan info` surface task rollup (e.g. "6/8 tasks done") or only plan-level metadata? `pkg/plan` already parses task statuses, so the rollup is cheap if wanted.
- Is `Completed` the terminal plan status, or should "done" be inferred from all tasks being `done`?
